## Findings requiring bounded UI correction

**F1 — P2: M2 raw downloads use the M5 epoch.** `app.js:1005` calls `m5Tai` for the M2 NATIVE button. That actual helper at760–767 captures/checks only `m5Epoch` before creating/clicking the download anchor. M2 role changes1105–1110/reset947–952 advance `m2Epoch`, not `m5Epoch`. Therefore an old source actor's M2 raw request may finish after switching the M2 display to a viewer without READ_SOURCE and still trigger a download. Server authorization could have been valid when the old request began; this finding concerns the required client context fence and does not claim a server ACL bypass. Add a bounded M2 download wrapper or an explicit M2-current predicate, checking the relevant M2 actor/selection epoch before download and error display. Preserve the M5 helper's existing behavior. A deferred response plus M2 role switch is the necessary negative; an unchanged-context nonempty download is its positive counterpart.

**F2 — P2: older same-selection GETs can overwrite a newer committed view.** `m2Detail:1033–1040` checks only actor/selection epoch and selected invoice, while `m2Load:1093–1101` also has no request generation. Refresh1103 and mutation refresh963 do not advance that epoch. A finite causal sequence is: existing detailA; manual refresh starts GET_A; CFO action commitsB; mutation refresh GET_B paintsB; delayed GET_A still has the same epoch/invoice and paintsA overB. The analogous older list response can replace `m2` at1100. Server expected_graph should reject a subsequent stale mutation; no database-corruption claim is made. Add a current read/render generation or equivalent fence for overlapping load/detail requests, including errors and nested detail refreshes. Independently verify the ordinary positive and the late-A-after-B negative; coherent server REPEATABLE_READ responses alone do not order their arrival in the browser.
